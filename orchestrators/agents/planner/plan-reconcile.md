# plan-reconcile — module for `--type sync` (reconcile shipped work against plan/ticket)

Type-specific guidance only; every invariant lives in the planner definition. The module emits **two artifacts**, and is not a repo sweep: the reconciliation **record** — `sync-report.md`, inside the reconciled plan's dir, unchanged home and role — and, when gaps require it, the reconciliation **plan** — written as `proposals/<slug>-MM-DD-YY.md` and becoming the run's `plan.md` on promotion; this is the artifact the §2.7 `--plan <path>` handoff adopts. If the reconciled plan is already in `completed/`, the caller reopens it first (`plan-lifecycle.sh reopen`) and passes the restored path; the planner never writes into `completed/`. The human gate confirms the classification table — the confirm gate WAS this plan's approval, which is why the §2.7 handoff skips the plan gate. The module writes files; it does not promote and does not gate — the caller (`sync.md`) promotes after the confirm gate, exactly as `diagnose.md` promotes the ranked report.

- **When every item classifies `done` or `dropped`: no reconciliation plan is written.** Say so explicitly, in the report and in the envelope, rather than emitting an empty syllabus — an empty plan would fail `validate-plan.sh` on "no `<phase>.<subphase>:` checkbox entries found."
- **Truth sources:** the plan syllabus and/or the Jira ticket's acceptance criteria (at least one), resolved through `--against`'s anchors, versus the REAL shipped diff (`git diff <base>...<ref>` over the shipped-work reference you were given). Read the diff yourself; never trust the plan's account of itself. Explore only as supporting evidence — e.g. confirming a claimed pattern is actually in place, not just present in a hunk.
- **Classify every item** — each syllabus subphase / acceptance criterion becomes exactly one of:
  - `done` — fully implemented and verifiable in the diff/code.
  - `partial` — started but incomplete.
  - `dropped` — explicitly decided against, evidenced in diff/commits or stated by the user.
  - `diverged` — done, but differently than planned; note how, and whether the divergence respects the project's conventions.
  Cite evidence (paths, hunks) for every classification; what you can't verify is `unverified` with an open question, never a guess.
- **`--against` is an array — the table gains a per-anchor column.** Every classified item names which anchor it came from (the ticket key, plan path, or git ref, as resolved). Anchors are resolved by `resolve-anchor.sh`; reference it, don't describe or duplicate its resolution logic.
- **`sync-report.md` sections:** Scope & Sources (plan path, ticket key(s)/anchors, base, shipped-work ref) · Per-Item Classification (item → status → anchor → evidence → notes) · Diff Summary · Open Questions / Unverified.
- **The reconciliation plan carries the full build grammar — every element `validate-plan.sh` and a builder need, by name:**
  - `## Phase syllabus` as the file's first `## ` section, title-only at both levels;
  - every phase decomposed into numbered `<phase>.<subphase>` checkboxes — a phase with no subphase entry is a format violation; a single-item phase still gets a `N.1`;
  - `(lane <n>)` annotations where the gap-closing work is separable, with disjoint file scopes between lanes carrying no edge between them — shared touchpoints get their own serialized integration subphase;
  - `(after: <ids>)` edges naming real subphase IDs, forming an acyclic graph;
  - exactly one detail block per syllabus checkbox (1:1, both directions), opened with its ID in markup the validator accepts — a bold lead-in (`**<id>:`) or a heading (`### <id> — Title`);
  - each detail block names, at minimum: its **file scope** (concrete paths — "somewhere sensible" is not a file scope), the **existing pattern or example to follow**, its **acceptance criteria**, and its **test approach**;
  - the acceptance criteria are the oracle and govern; the named pattern supplies style and structure, not behavior — where a subphase intentionally departs from the behavior of the pattern it names, the detail block says so explicitly rather than leaving the reader to find the contradiction;
  - acceptance criteria must be **sufficient, not merely present** — concrete enough that a blind test author can derive executable tests from the detail block alone, the bar `plan-feature.md` already sets for its own type. Where a subphase's observable behavior is an error path whose only output is a message, fix the exact user-visible text and the exit-status family: the coder and the contract-tester can't see each other's work, so an unfixed message string means each invents a different one;
  - each detail block declares its **test oracle** from the closed set — `new contract tests` | `existing suite` | `equivalence check` | `existing implementation`;
  - the plan's other `plan-format` required sections: Goal & scope · Stack & MAJOR versions (with the manifest/lockfile each was verified from) · Conventions to enforce · the phased subphase sections · Risks/open questions/decision points · Skill mapping;
  - never a time estimate.
- **A builder handed one of these lanes writes its packet contract without asking a question.** Lane names alone are not dispatchable — that is the acceptance bar this module is tested on; detail blocks are not optional garnish on a lane list.
- **An open decision that would change a subphase's acceptance criteria blocks that subphase, not the plan.** The reconciliation plan may carry genuine decision points (`plan-format`'s Risks/open questions/decision points section), but the §2.7 handoff adopts this plan into a build run that skips the plan gate, so a question left open here has no later human checkpoint to land on. Put it to the human at the **confirm gate** (the gate that already IS this plan's approval) and record the answer in the plan; a subphase whose criteria still depend on an unresolved decision is marked **not dispatchable**, never shipped as if it were ready. A builder must never have to guess a decision the plan itself flagged as open.
- **Oracle default for reconciliation subphases:** gap-closing work is finishing work that was already specified, so declare `existing suite` where the shipped test surface already covers the area (the anti-cheat oracle `plan-rework.md` names), and `new contract tests` for any behavior the reconciliation adds that no existing test covers. An `existing suite` declaration names the suite **and its limits** — where the pre-existing suite lacks the idiom the new cases need (no assertion helpers, no stderr/exit-code pattern, cases running under `set -e` so a failing command aborts the file), the detail block says so; naming a file is not the whole oracle.
- **You change nothing else.** The record stage — after the human confirms — ticks the plan syllabus, updates docs, and transitions the ticket per your table; you only produce the table and, when gaps exist, the reconciliation plan. Items the user wants actually finished are a hand-off to a build run; say so rather than softening a `partial` into a `done`.
- Envelope back: `artifacts[]` = [report path] and, when written, [reconciliation plan path]; body = the classification counts, the notable divergences, the open questions, and the lane/subphase count of the reconciliation plan — or an explicit statement that no gaps require one.
