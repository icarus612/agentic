# report — the map / analyze workflow (`--type map`, `--type analyze`)

For a question that needs an ANSWER, not a code change: a fast read (`map`) or a rigorous one (`analyze`) over the codebase, delivered as a structured report. The router hands this file the run's already-resolved axes — `explore` depth, the rigor profile (`RIGOR_EXPLORE`, and `RIGOR_PR` when the run has a PR phase), `ship`, and the row's `branch:` prefix where one exists — plus the user's question VERBATIM; this file's job starts after resolution. One file serves both types because `map` and `analyze` are the same pipeline at different presets: they differ ONLY in the axis values their `workflows.yaml` rows set, never in shape. Every branch below is on a resolved axis VALUE (`ship`, `rigor`), never on the type name — that is the only thing keeping the two presets from drifting apart, and it is why this is one file and not two.

`map` is a cheap `analyze`: it skips the publishing pre/post run steps entirely. It is cheaper because it

- **explores less** — `explore: auto`, which MAY resolve to SHALLOW; that is intended, not a shortfall, and `map`'s depth is never aligned with `analyze`'s `deep`;
- **verifies less** — `rigor: low`: one explorer, no committee;
- **loads none of the publish seam.**

It is not cheaper because it writes a shorter document — an output-length axis was proposed and rejected, and nothing here reintroduces one by implication. `--explore` remains a free dial on `map` and `analyze` alike, the row value a default rather than a prohibition — exactly what distinguishes it from `ship`, which resolves to the row's value only and accepts no flag at all (see Setup, below).

## Stages

**1. Setup, branching on `ship`.** The two ship modes diverge completely at the entry point.
- **`ship: chat`** — Setup is SKIPPED ENTIRELY, and with it everything it drags in: no `workflow-setup.sh`, no branch, no parent worktree, no run dir, no `progress-log.md`, no docs-target resolution, no `push-pr` at any stage, no `cleanup-merged`. None of the publish seam loads — nothing loads "just in case" here. What replaces Setup is the **scratch dir**: invoke `resolve-scratch.sh --slug <slug>` (`<slug>` a short slug of the question) and take the path from its `SCRATCHDIR:` line rather than assembling it — the same contract `dae/SKILL.md:111` already states for `workflow-setup.sh`'s `RUNDIR:` line; the script creates the dir itself, so there is no separate `mkdir -p` step. It must work when the cwd is not a git repo at all, and it is resolved before the Explore stage starts, so a crashed run leaves its claim files recoverable — it is not under the run-dir conventions, and it gets no `progress-log.md`. The resolved path carries a run id: without one, two concurrent runs — the same question run twice, or the same question run from two different repos — would collide on one directory, and a report run has no branch to protect it the way a worktree run does. State the resolved path to the user in chat. `resolve-scratch.sh` owns the resolution ladder and the variable name (see `artifact-locations`); neither is restated here.
- **`ship: publish`** — the router's shared Setup stage, referenced not restated. Branch type comes from the resolved row's `branch:` (the existing `docs/` prefix `workflow-setup.sh` already accepts — do not invent a new prefix and do not propose widening its enum). Artifacts live in the run dir; the scratch dir is not used at all in this mode.

Worktree need is decided by these two axes and nothing else:

| `ship` | `rigor` | needs |
|---|---|---|
| `publish` | any | the shared Setup stage — full parent worktree + branch; it commits |
| `chat` | `low` | nothing; read the live cwd — genuinely fast |
| `chat` | `≥ med` | a pinned snapshot: a detached worktree at `HEAD`, no branch, removed when the run ends |

At `rigor: low` there is one explorer, and one reader cannot disagree with itself — reading the live cwd is harmless. At `rigor ≥ med` there are 3-5 explorers reading over minutes; if the tree moves underneath them they disagree because the tree moved, which routes into the committee's dispute logic and turns it into noise. Build, diagnose, document and sync runs are already safe from this: their gates read a parent worktree pinned to a branch nobody else is touching, and the orchestrator serializes gates, so no race is possible. The exposed flow is exactly the `ship: chat` report run reading the live cwd — the tree the user may be editing right now. No git repo means no snapshot is possible: warn and proceed, never block.

The `chat`/`≥ med` cell is reachable today and not hypothetical: `--rigor` stays a free dial, so `dae map --rigor med` produces `ship: chat` at `rigor: med`.

Mechanics, kept minimal and stated here because no other file owns them: `git worktree add --detach <scratch-dir>/snapshot HEAD`, members read there, `git worktree remove` at the end. It goes under the scratch dir rather than the workflows dir on purpose — `worktree-modes.md:11` lists worktrees on disk in the workflows dir as resumable run candidates, and a snapshot is not a resumable run. This removal is not on `allow-workflow-cleanup.sh`'s auto-allow list (`:112-122` — case 2 auto-allows only a path whose basename matches `-l[0-9]+$`), so it may prompt; prompting is fine, and widening that allowlist is not in scope.

**2. Explore (the collector), branching on rigor.** Invoke the **`explore`** skill via the Skill tool with the resolved depth and an explicit output path — inside the scratch dir at `ship: chat`, inside the run dir at `ship: publish`. Carry the map's PATH forward into stage 3, never its content — pass pointers, not payloads.
- At `rigor: low` — invoke `explore` DIRECTLY: the existing solo path, unchanged. This is NEVER `committee(explore, n=1)`; a `low` report run produces NO `committees/` directory at all. Treating `low` as "a committee of one" would put every currently-working behavior downstream of new code for no benefit — the direct call runs the existing code path unchanged.
- At `rigor ≥ med` — wrap `explore` in the `committee` agent at the tier's width. `committee.md` owns the member-file layout — point at it, never restate it. The one fact that is this file's business: at `ship: chat` that same relative layout roots under the scratch dir, because there is no run dir.
- `against: forbid`: this middle NEVER resolves anchors and never loads `resolve-anchor`. A violation is already an error at parse time, before Setup runs.
- No `init-workspace` — a report run builds and installs nothing.

**3. Write the report against the skeleton.** Fill `report-skeleton.md` (its sibling file, named for the frame it is). The frame is fixed and the interior is dynamic; the five sections are that file's contract — point at it, don't re-list their internal requirements here. The report is written to disk in BOTH ship modes: `report.md` in the scratch dir at `ship: chat`, the record target (stage 5) at `ship: publish`. At `rigor ≥ med`, section 4's evidence sources from the committee's consolidated `accepted.md` — never from an individual member's claim file.

**4. Deliver — `ship: chat`'s terminus.** Answer the question IN CHAT, in full, and state the scratch path. This is the one place pointers-not-payloads does not apply: the consumer here is the human, not a downstream agent. Then **STOP**: no Record, no Ship, no PR gate, no `push-pr`, no `cleanup-merged`, no syllabus, no plan, no `plan-lifecycle.sh`. The observable property: no branch, no commit, nothing staged, and nothing that reaches the product branch — plus, at `rigor: low`, no worktree either. Anything a chat run writes that reaches the product branch is a defect in this file, not a tolerable side effect; a gitignored scratch-dir write and a temporary `rigor ≥ med` snapshot are permitted by construction.

**5. Record + Ship — `ship: publish` only** (shared — router; referenced, never restated). Record: invoke **`document-local`** to record the report under the resolved docs root's `reports/` subdirectory — `<docs-root>/reports/<slug>-MM-DD-YY.md` (with the default docs root that renders as `docs/reports/`). State it in terms of the RESOLVED root; hard-coding `/docs` would break the `CLAUDE_DOCS_DIR` chain. No publish step, no mode branch — the same shape `document.md`'s Record stage ships, not a second one. `analyze` and `document` differ in WHAT they publish and WHY, never in WHERE or HOW. The draft PR opens at the record commit, for the same reason `document.md` opens there: no planner and no builders means nothing is committable before Record, so the record commit is the earliest point a draft PR can open — reference the shared **Open the draft PR** step by name. Then the shared **Ship** stage: commit + `push-pr --stage update` before the PR gate, the PR gate, then `push-pr --stage finalize`. Reference; never restate the mechanics, never re-describe the confirmation cadence. **PR-gate spec of record:** the question as asked, plus the report itself. **Scope boundary: nothing outside `<docs-root>/reports/` may have changed** — this is the acceptance property that `analyze` produces a branch touching only `docs/reports/`, and it must be the gate's stated scope boundary, not an aside; pages a CI job later publishes from this tree are downstream output, outside the gate's scope. `rigor` at the `pr` phase exists only in this mode: when `RIGOR_PR ≥ med` the PR gate wraps in the committee exactly as at every other gate — one sentence and a pointer, no new machinery.

## Notes

- If answering the question turns out to require CHANGING code, stop and bring it to the user — recommend a build or diagnose run; a report run never writes source (mirrors `document.md`'s note).
- Read-only in both ship modes: the only files a report run writes are its own report, the explore map, and the committee artifacts.
- The chat run's interruption story is deliberately weaker than a worktree run's — acceptable because a re-run is cheap and leaves nothing on any branch; the scratch dir existing on disk (stage 1) is what keeps a crashed run's claims recoverable.
